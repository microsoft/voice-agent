# Multi-Stage OTP Verification Showcase - Projects SDK sample

## Conclusion

This sample publishes a Contoso Bank caller-verification demo. A hub node
explains four verifications and lets the caller try them in any order. When a
check passes, the Agent names the verified customer, explains what a real
deployment would do next, then clears the verification and returns to the hub.
Only the MCP backend decides whether a check passed.

| Verification | The caller... | The backend checks |
| --- | --- | --- |
| identity | Says their name, picks themselves from up to three matches, gives their birthday | Phonetic name search, then that customer's month and day of birth |
| KBA | Is already known to the bank (outbound, default You Meng) and gives their birthday | Month and day of birth |
| OTP | Reads an 8-digit one-time code generated on the web page | The code is valid, unused and unexpired; its owner is who the caller is |
| SMS | Reads a 6-digit code texted to the phone | The code matches and is unexpired |

The hub reports results from the backend, never from the model's judgement.

## Call flow

```text
$entrypoint -> hub

  hub --> identity --> identity_verified --> hub
  hub --> kba      --> kba_verified      --> hub
  hub --> otp      --> otp_verified      --> hub
  hub --> sms      --> sms_verified      --> hub
  hub --> end
  (a check that fails, locks, is stopped or is switched returns to hub)
```

| Node | Tools | Leaves when |
| --- | --- | --- |
| `$entrypoint` | none | The caller's first turn, to `hub` |
| `hub` | `start_call` | The caller picks a check; the caller is done -> `end` |
| `identity` | `find_customer`, `verify_identity` | Passed -> its own `*_verified`; locked, stopped or switching -> `hub` |
| `kba` | `verify_identity` (method kba) | Passed -> its own `*_verified`; locked, stopped or switching -> `hub` |
| `otp` | `verify_access_code` | Passed -> its own `*_verified`; locked, stopped or switching -> `hub` |
| `sms` | `send_sms_code`, `verify_sms_code` | Passed -> its own `*_verified`; locked, stopped or switching -> `hub` |
| `identity_verified`, `kba_verified`, `otp_verified`, `sms_verified` | none | One per check: names the verified customer, explains what that check unlocks, clears the verification -> `hub` |
| `end` | `end_call`, `end_conversation` | Terminal |

The hub calls `start_call` once on every arrival, including the first, so
every check starts from a fresh session and every name and result comes from
the backend. Every transfer into a check speaks a
fixed introduction of how it works and what it checks.
The greeting introduces the four verifications. A check that passes hands
off to its own verified stage, which names the verified customer (for OTP, whom the code
identifies), explains what a real agent would do at this point, and asks
whether to go back. It calls no tool. On the caller's answer it hands off to
the hub with a fixed transfer message saying the verification is cleared; that
message plays while the hub opens the fresh session, so there is no long
silence. The hub then asks what to try next.

## Name search

Recognizers often mishear names, so the search never decides alone. It
returns up to three choices. A confidently matched full name comes back as
`likely` and the Agent asks "Am I speaking with ...?"; anything else, including
a single or run-together word such as "mengyou", comes back as `choose` and
the Agent reads the names for the caller to pick. If none is right, the caller
says the name again. A picked name is not a verification: the birthday check
decides.

## Security behaviour

- One call verifies one customer. KBA and SMS check the customer the call is
  for. Before anything has passed, identity binds the call to the customer the
  caller picked, and OTP binds it to the code's owner, so anyone can start
  with their own code.
- Within one verification session, once a check has passed the customer is
  fixed: identity cannot pick someone else, and another customer's access
  code is rejected and is not used up. In this demo the hub opens a new
  session on every arrival, so each check starts clean.
- Only the month and day of birth are checked. An unclear date costs no
  attempt, a wrong one does, and the Agent never says which detail was wrong.
- The Agent passes only the digits from the caller's last turn; the backend
  accumulates partial codes at no cost.
- Each verification allows 3 attempts, then locks for this call. The others
  stay available.
- The Agent never reads back a code, and the SMS code is never returned to it.

## Test data

There are 20,013 fictional customers: 21 hand-made ones
([`otp_candidates.json`](../../shared_mcp/app/shared_mcp/ex35_auth_ladder/otp_candidates.json))
plus 19,992 generated by
[`build_bulk_customers.py`](../../shared_mcp/app/shared_mcp/ex35_auth_ladder/build_bulk_customers.py)
from the 20K-name directory the phonetic name search was benchmarked on. Any of them can pass identity or OTP; the OTP console shows each
customer's date of birth.

| Item | You Meng (default) | Jeremy Downer |
| --- | --- | --- |
| Say your name as | "You Meng" | "Jeremy Downer" |
| Date of birth (month and day checked) | April 16 (1988) | September 18 (1987) |
| Permanent access code | `12345678` | `87654321` |
| Phone on file | +1 (425) \*\*\*-4821 | +1 (248) \*\*\*-9012 |

- Text-message code: `246810` works for any customer. Unless the MCP host has
  Twilio configured, no text is really sent.
- One-time access codes: generate one for any customer in the OTP console
  below. It works once, for 48 hours, and identifies that customer.
- To try Jeremy Downer, start with OTP and read `87654321` (or a code
  generated for him), or start with identity and say his name.

## Try these turns

- After the greeting, say "Let's do KBA." When told the call is for You Meng,
  say "April sixteenth." Expect "KBA check passed. You are verified as You
  Meng.", a note on what a real agent would do next, and "Shall we go back?"
  Say "Yes." The verification is cleared and the hub asks what to try next.
- Say "OTP." Open the OTP console, generate a code for any customer (or use
  the permanent code 87654321), and read it in two parts, such as "8 7 6 5"
  then "4 3 2 1". Expect "That code identifies Jeremy Downer." Answer "Let's
  do SMS next." to go straight to the next check.
- In SMS, when asked for the text-message code, say "2 4 6 8 1 0", the
  fictional test code.
- Say "Identity." When asked for your name, say "Sheng Zhao" or even
  "mengyou"; pick the right name from those read back, then give the birthday
  (Sheng Zhao: November 2; You Meng: April 16).
- Say "That's all, thanks." Expect a goodbye.

Also try: inside any check, say "SMS instead" to switch; the hub takes you there; a wrong
birthday three times locks that check for this call.

## OTP console

The `/otp` console's page and logic are served at `/ex35-otp` on the same host
as the MCP routes:
<https://voice-agent-noauth-mcp.lemonsky-36682081.westus2.azurecontainerapps.io/ex35-otp>.
The picker holds about 20,000 fictional customers: type part of a name to filter by spelling, or open the list to browse everyone; when no spelling matches, the phonetic name search suggests names that sound alike (for example "jung new" finds Zheng Niu). Select a customer and generate an 8-digit code. Codes live in this sample's
own store, so generating one never replaces a code issued for another route
on the same host. The page is open like the no-auth MCP routes; set
`EX35_OTP_ADMIN_TOKEN` on the host to require an administrator key.

## MCP service

| Item | Value |
| --- | --- |
| Route | `/mcp/ex35-auth-ladder` on the public no-auth MCP (verifications and name search) |
| Name search alone | `/mcp/ex35-name-search` |
| OTP console | `/ex35-otp` |
| Tools | `start_call`, `find_customer`, `verify_identity` (kba or identity), `verify_access_code`, `send_sms_code`, `verify_sms_code`, `get_auth_status`, `end_call`; no prefix, the route is the namespace |
| Auth | None. The Agent binds a direct `server_url`; there is no Project connection. |
| State | Sessions and codes in shared Redis on the no-auth host, memory locally |
| Verification source | [`shared_mcp/app/shared_mcp/ex35_auth_ladder`](../../shared_mcp/app/shared_mcp/ex35_auth_ladder) |
| Name search (`find_customer`) | Provided by the public no-auth host only; it is not part of this repository |

The public host runs its own deployment of these packs; the source here is the
reference copy and is not deployed from this repository automatically.

## Publish and run

```bash
cp .env.example .env   # set AZURE_AI_PROJECT_ENDPOINT
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python sample.py publish
.venv/bin/python sample.py run --expect-mcp --expect-handoff \
  --message "Let's do KBA." \
  --message "April sixteenth." \
  --message "Now OTP." \
  --message "1 2 3 4 5 6 7 8" \
  --message "That's all, thanks."
```

Leave `VOICE_AGENT_MCP_CONNECTION_ID` empty for the no-auth MCP. Set it only
when you host the packs yourself behind a Project connection.

## Limits

- SMS: the backend texts the code through Twilio when the MCP host has
  `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_SMS_FROM` and
  `EX35_SMS_TO` set. The public host does not have them yet, so the send is
  simulated and `246810` is the way to pass.
- Precomputed name spellings are curated by hand.
